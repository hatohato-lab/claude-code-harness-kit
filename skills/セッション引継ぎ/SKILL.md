# セッション引継ぎ

最も大事な手順を先頭に置いています。圧縮のあとに読み直されるのは、スキルの先頭の部分だけのためです。

## 目次

1. 全体の流れ（省略しない4手順）
2. 作業一覧の形（並べ方と番号の受け取り方）
3. 作業一覧のコマンド（生ログから時間順に抽出）
4. 引き継ぎ書の中身（この順に並べる6節）
5. 新しいセッションへの渡し方（貼る2行のひな形）
6. セッション情報の表（引き継ぎ書の末尾に付ける）
7. 引き継ぐ根拠（圧縮の要約に頼らない理由）
8. 禁止（やらないこと）

## 1. 全体の流れ（省略しない4手順）

1. このセッションの作業を時間順に並べた一覧を出し、引き継ぐものを番号で選んでもらいます。
   番号が返るまで、ここで止まります。
2. 選ばれた番号の作業だけで引き継ぎ書を書き、プロジェクトの中の引き継ぎ用フォルダに保存します。
   ファイル名は `<セッション名>_<yyyyMMdd_HHmm>_引き継ぎ書.md` です。
   引き継ぎ用フォルダが無ければ、どこに作るかをユーザーに1行で聞きます。
3. 保存したパスと「新しいセッションに貼る2行」を、1つのコードブロックで見せます。
4. 確かめ方を1行そえます。「新しいセッションで『引き継ぎ書の要点を3行で』と言わせ、読めたのを確かめてから古いほうを閉じる」。

/compact は使いません。ユーザーにも打たせません。圧縮の要約には一切頼りません。
引き継ぎ書は、いまのコンテキストにある記憶と生ログから、自分で書きます。

## 2. 作業一覧の形（並べ方と番号の受け取り方）

機械的に並べると、規則どおりの項目しか残りません。
どれを持っていくかはユーザーの判断が要るので、選ぶ手続きを必ず挟みます。

一覧はこの形で出します。番号、時間帯、作業名の3つだけです。

```
1  09-20 20:38〜21:10  退避した30件をルールのフォルダへ戻した
2  09-20 21:10〜22:30  ルール47件の重複6組を検出
3  09-21 00:30        ルールの設計書をTODOに登録

番号で選んでください（全部なら「全部」）
```

書き方は4点です。

- 作業名は25字前後の具体名にする。「作業」「対応」「確認」のような一般語は使わない
- 時刻は生ログの実測値。1件だけの作業は開始時刻だけ書く
- 10行を超えたら、近い話題をまとめて10行以内にする
- 最後の1行「番号で選んでください（全部なら「全部」）」は必ず付ける

番号が返ったら、その作業だけを引き継ぎ書に書きます。
選ばれなかった作業は、6節のどこにも書きません。

## 3. 作業一覧のコマンド（生ログから時間順に抽出）

作業フォルダで、プラグインの `scripts/session_log.py` を実行します。
このスキルのフォルダから2つ上の階層にあります。`python` が無ければ `python3` を使います。

```
python <プラグインのフォルダ>/scripts/session_log.py msgs <自分のセッションID> all
```

自分のセッションIDは、スクラッチパッドのパス（`.../<セッションID>/scratchpad`）に入っています。
見つからなければユーザーに1行で聞きます。推測しません。

出た時刻を、話題の切れ目でまとめて1行にします。
圧縮より前の発言もここに出ます。要約に無くても、生ログには残っているためです。

## 4. 引き継ぎ書の中身（この順に並べる6節）

1. 作業名と現在地 …… 何の作業で、どこまで終わったか。3行以内
2. 決定と理由 …… 決定1件につき「決定＋なぜ」を1行ずつ。理由は書かない限り消える
3. 未承認と保留 …… ユーザーの承認や判断を待っているものの一覧。勝手に進めない印
4. 成果物 …… 絶対パスを1件1行で
5. 次の一手 …… 新しいセッションが最初にやること。1〜3件
6. 取り直しのコマンド …… 消えたデータを取り直すコマンド。一時フォルダの結果は消えるので、要るものは本文かプロジェクトへ写してから書く

## 5. 新しいセッションへの渡し方（貼る2行のひな形）

```
<保存した引き継ぎ書の絶対パス>
を読んで、要点を3行で言ってから「次の一手」の1から続きを始めて
```

## 6. セッション情報の表（引き継ぎ書の末尾に付ける）

```
python <プラグインのフォルダ>/scripts/session_log.py info <自分のセッションID>
```

出た名前、セッションID、稼働期間、圧縮回数、ログの大きさを、引き継ぎ書の末尾に表で付けます。

## 7. 引き継ぐ根拠（圧縮の要約に頼らない理由）

| 症状 | 圧縮で起きていること | 出典 |
|---|---|---|
| 存在しないパスを言う | 圧縮の直後に読み直すファイルは5件だけ。大きいものは中身なしのパスだけ戻る | 1 |
| 決めたことを蒸し返す | 圧縮前の思考は引き継がれない。判断の理由だけが消える | 2 |
| ルールを守らない | paths 付きのルールと下の階層の CLAUDE.md は、要約で消える | 1, 3 |
| 全体に精度が落ちる | 会話が長いほど品質が落ちると、公式が明言している | 2, 4 |

「圧縮N回で引き継ぐ」という公式のしきい値はありません。

出典は次の4本です。

1. https://code.claude.com/docs/en/context-window#what-survives-compaction
2. https://platform.claude.com/docs/en/build-with-claude/compaction
3. https://code.claude.com/docs/en/memory
4. https://www.trychroma.com/research/context-rot

## 8. 禁止（やらないこと）

- /compact を提案しません。打たせません。
- 一覧を出さずに引き継ぎ書を書き始めません。番号が返る前に保存しません。
- ほかのセッションの生ログを開きません。
- 要るデータを一時フォルダに置いたままにしません。
- 要約に無いことを「決まっていた」と言いません。
- 取れなかった項目は「不明」と書きます。推測で埋めません。
