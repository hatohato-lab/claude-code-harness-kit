# スキルの書き方

スキルをブラックボックスにせず、人が自分で読んで直せる状態を保つための書き方です。

## 目次

1. フォルダの形（1スキル1フォルダ、中に SKILL.md）
2. 先頭の書き方（name と description）
3. 見出しの書き方（概念＋かっこの説明）
4. 番号と目次（リンクは付けない）
5. 残すもの（読む人に推測できない情報だけ）
6. 削るもの（git で追えるもの、繰り返し）
7. 言葉づかい（公開するものはですます調）

## 1. フォルダの形（1スキル1フォルダ、中に SKILL.md）

スキルは必ずフォルダを作り、その中に `SKILL.md` を置きます。
`.md` をフォルダに直置きしても、スキルとして認識されません。これは Claude Code の仕様です。

フォルダにする理由は、参照用の別ファイルやスクリプトを一緒に置けるようにするためです。

```
.claude/skills/<スキル名>/
├── SKILL.md      必須
├── reference.md  任意（詳しい資料を分けたいとき）
└── scripts/      任意（スクリプトを置くとき）
```

## 2. 先頭の書き方（name と description）

`---` で囲んだ部分に書きます。`name` は1行です。`description` は複数行に分けてかまいません。

```
---
name: スキルを作る

description: >-
  ①スキルを新しく作るときの手順です。
  ②「スキルを作って」で発火します。
---
```

`>-` は「改行を空白1つに畳む」という YAML の記法です。
ファイルの中では複数行に見えますが、読み込まれるときは1行に戻ります。

`name` の下の空行は、YAML では無視されます。人が読みやすいように入れています。

`description` は、Claude がこのスキルを呼ぶかどうかを判断する文です。
何のスキルか、いつ読むかの2つを必ず入れます。

## 3. 見出しの書き方（概念＋かっこの説明）

見出しは「概念（説明）」の形にします。

```
## 出力の保存場所（出力の保存先2か所）
```

左の概念で何の話かが一瞬で分かり、右のかっこで、何件あるか、どういう内容かが分かります。
左だけを縦に拾い読みすれば全体像がつかめて、必要なところだけかっこの中を読めます。

悪い例は「結果」「まとめ」「確認」です。中を読まないと何の話か分かりません。

## 4. 番号と目次（リンクは付けない）

見出しに `1.` から順に番号を振ります。
先頭に目次を置き、見出しをそのまま並べます。リンクは付けません。

見出しに id を付けないビューアでは、押しても飛ばないリンクが混乱のもとになるためです。

## 5. 残すもの（読む人に推測できない情報だけ）

- なぜそうするかの理由（AI が形を変えたくなったときに止まる材料になる）
- 実際に起きた失敗（抽象的な注意より効く）
- ユーザーの読み方と使い方（AI には推測できない）
- 意味を伝えるユーザーの言葉（言い換えると意図がずれる）

例: 「ユーザーはチャットから番号をコピーして、検索窓に貼る」。
これが書いてあると、なぜコードブロックで示さなければならないかが分かります。

## 6. 削るもの（git で追えるもの、繰り返し）

- 作成日と、日付つきの経緯の引用（git の履歴で追える）
- 題名の「（全プロジェクト共通・厳守）」のような飾り（全部に付くと区別にならない）
- 存在しないルールへのリンク（開けないので害だけ）
- 同じことの言い換え（見出しに書いたことを本文で繰り返さない）

## 7. 言葉づかい（公開するものはですます調）

GitHub へ公開するリポジトリの文書は、ですます調で書きます。README、CHANGELOG、SKILL.md が対象です。

自分の環境の中だけで使うスキルは、短く書くほうを優先してかまいません。
